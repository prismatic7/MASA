# MASA protocol audit — 2026-07-29

Status: completed local audit and hardening pass  
Scope: this repository's working tree only  
Protocol and reference implementation: `0.1.0` unreleased local working line

## Conclusion

MASA now functions as a project-agnostic protocol and an independently packable local reference implementation. No application runtime is required to validate a record, inspect a bundle, trace causal lineage, audit a public projection, use the CLI, or launch the read-only MCP server. Application integrations remain namespaced adapters rather than conformance dependencies.

The audit found one normative absence-state contradiction, incomplete lineage direction semantics, several semantic-validation gaps, application vocabulary inside shared fixtures, and a packaging defect that made installed CLI and MCP artifacts depend on a repository checkout. These were repaired without changing the declared protocol version because `0.1.0` has not been released. The compatibility rationale and release constraint are recorded in `CHANGELOG.md`.

## Baseline findings and disposition

### Normative model

- **Repaired:** the protocol required unknown, withheld, unavailable, deleted, and not-applicable to remain distinct, but a known qualified value could still contain `null`, and other positive assertion fields also accepted `null`.
- **Repaired:** deletion lacked a first-class qualified state with a receipt trail. Qualified values and tool/schema-reference states now support a distinct `deleted` branch with a reason and deletion-receipt references.
- **Repaired:** shared register and scale fields were closed to only the initial MASA list. They now accept either Core values or a namespaced extension value, so an unrelated project can extend classification without editing MASA.
- **Repaired:** completed transformation lineage accepted only a subset of registered inverse relations. The relation registry now states which endpoint is the descendant, and inverse terms are checked for reciprocal direction.

### Validation and policy

- **Repaired:** local references were checked mainly for existence. The validator now also verifies protocol roles such as actor, source, policy, event, representation, claim, context, and listening-pass references.
- **Repaired:** timestamps could be individually valid while declaring a reversed interval. Operation, window, freshness, and policy-validity ordering now receive deterministic diagnostics.
- **Repaired:** a public `permitted` evaluation could cite an active public policy without proving that a matching rule allowed the exact publish action and target. Publication audit now requires that rule, known authority, matching validity, and no matching prohibition.
- **Improved:** non-healthy source health and unknown freshness without a reason receive non-breaking warnings rather than silently losing operational context.
- **Improved:** public-audit diagnostics returned by the MCP boundary are deduplicated.

### Lineage, CLI, and MCP

- **Repaired:** lineage tracing was direct and predicate-shape dependent. The shared core now provides deterministic breadth-first traversal for ancestors, descendants, or both, with a default depth of 16 and a hard cap of 64. Unknown extension predicates are preserved but never guessed into causal lineage.
- **Expanded:** the CLI has `masa lineage <record> <entity-id>` with direction and depth controls.
- **Expanded:** `matter.trace_lineage` now returns a bounded transitive causal subgraph. MCP conformance exercises the tool over stdio, not only its advertised capability.
- **Preserved boundary:** MCP remains read-only, stdio-only, offline, and confined to explicitly configured real paths. Symlink escape and remote-URL inputs remain refused.

### Packaging and project independence

- **Repaired:** the packed CLI and MCP previously searched for schemas, capabilities, and specification files relative to a repository root that is absent after installation. Versioned schemas, capabilities, and protocol resources are now generated into and loaded from package code.
- **Repaired:** artifact inspection used an npm packing path that did not model pnpm workspace dependency rewriting. It now uses `pnpm pack --dry-run`.
- **Expanded:** the release gate packs all five local packages, extracts them into an isolated temporary installation, verifies that no `workspace:` specifier remains, imports every library, invokes both command entry points, and checks embedded schemas and capabilities.
- **Preserved boundary:** all packages remain `private: true`. The artifacts are tested as local packages; no registry publication is claimed or performed.

### Project-agnostic language

- **Repaired:** shared mapping and generation examples carried concrete application vocabulary. Shared fixtures now use the reserved `example:` namespace and generic adapter descriptions.
- **Clarified:** application names may appear in informative adapter documents and repository history, but never as normative schema requirements or reference-runtime dependencies.
- **Documented:** `docs/project-agnostic-integration.md` defines the adoption path for ordinary software, scripts, archives, instruments, and agent hosts.

## Compatibility decision

The assertion-null family is treated as one deliberate defect repair in the unreleased `0.1.0` working line:

- `{ "state": "known", "value": null }`;
- `Measurement.value`;
- `Claim.content` and `Claim.value`;
- `Context.content`;
- `Threshold.value`;
- `OperationReceipt.determinism.seed`.

All now require a non-null JSON value when present. Missing or protected knowledge uses a qualified absence state; omission means the profile does not assert the field. A repository-wide search found no such null assertion in any valid fixture or coordinated adapter, and regression tests cover every repaired field. Once a MASA version is released, a patch must not invalidate previously conforming records; an equivalent post-release change requires the versioning and migration procedure.

## Security and performance posture

The implementation remains offline by default. Bundle inspection is streamed and bounded; ZIP paths, links, encryption, duplicate normalized paths, undeclared entries, expansion ratio, per-entry size, total size, JSON size, and NDJSON line size are checked. Bundle promotion occurs only after complete verification. Core and validator packages perform no filesystem or network access. Indexing and lineage traversal use maps and adjacency lists rather than repeated whole-record scans.

The protocol validates accounts and provenance; it does not decode hostile audio codecs, execute models, authenticate hosted users, grant network authority, erase third-party caches, or establish the truth or legitimacy of a claim. Those remain host responsibilities or future versioned capabilities.

## Remaining expansion boundaries

These are deliberate non-blocking boundaries, not claims of completed functionality:

1. Cross-language SDKs and interoperability fixtures beyond the TypeScript reference implementation are not yet present.
2. Cryptographic signatures, transparency logs, and remote registry resolution are not part of Core 0.1.0.
3. MCP write operations remain absent. A future write capability needs an explicit output root, authorization, receipts, cancellation semantics, and atomic commit behavior.
4. Application adapters still need implementation-level conformance evidence in their own repositories; an informative MASA adapter document does not prove integration.
5. Audio decoding, feature extraction, synthesis, and data-provider acquisition belong to adopting systems. MASA records their methods, policies, uncertainty, and lineage rather than pretending to implement them.

## Recommended adoption gate

An adopting project should pin MASA `0.1.0`, declare only profiles it actually implements, choose its own namespace, preserve unsupported extensions, create operation receipts at effect boundaries, run its own exact conformance evidence, and keep application-specific validation inside its adapter. Shared MASA terms should be promoted only through a versioned RFC with evidence from at least two independent implementations.
